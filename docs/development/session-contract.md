# عقد إغلاق الجلسة واستمرارية العمل

## الغرض

يحدد هذا العقد الحد الأدنى لإثبات العمل عند الانتقال بين جلسات أو بيئات قد تكون مؤقتة. المحادثة والذاكرة البشرية تساعدان على السياق، لكنهما ليستا مصدر الحقيقة الهندسية؛ المصدر القابل لإعادة البناء هو Git وما يمكن فحصه وتشغيله في المستودع.

## قواعد الإثبات

- **لا diff مفحوص، بما في ذلك الملفات الجديدة، فلا ادعاء.** لا تُكتب أوصاف التغيير أو نصوص PR أو ChangeLog قبل فحص التغييرات الفعلية.
- **لا commit، فلا عمل مكتمل قابل للتحقق.** يجب أن يسجل commit العمل المقصود؛ التغييرات المحلية غير المثبتة ليست تسليمًا.
- **لا push، فالعمل غير دائم خارج بيئة الجلسة.** لا يُعد العمل متاحًا لجلسة أو بيئة أخرى حتى يُدفع إلى الفرع البعيد المقصود.
- **لا تبدأ `M(n+1)` قبل التحقق من `M(n)`.** يجب تثبيت مخرجات المرحلة واختبارها وفحصها قبل البناء عليها.
- **الأثر يسبق السرد.** الترتيب هو: `diff → tests → docs → PR description / ChangeLog`. يجب أن تصف الوثائق والملخصات ما يثبته الكود والاختبارات فعلًا، لا ما توقعناه أن يتغير.
- لا يُعاد بناء عمل مفقود من وصف شفهي أو سجل محادثة. انتظر commit أو patch يمكن فحصه، ثم سجّل ما يظهر فيه فعلًا.

## الثوابت تسبق الخطط

الثوابت الموثقة للمكوّن هي المرجع الأعلى من الرؤى أو خارطة الطريق. لا تُعامل فكرة مستقبلية على أنها إذن لتغيير سلوك أو حدود أمان. في `cela.sh`، يظل `dry_run=true` و`execution_enabled=false` قفلين إلزاميين؛ أي تغيير لهما يحتاج قرارًا هندسيًا ومراجعة مناسبة للسياسة ونموذج التهديد والاختبارات والتوثيق قبل تنفيذه.

وبالمثل، يجب أن تتبع خيارات النماذج والمزودات الحدود الموثقة للمكوّن المعني. لا تعني عبارة عامة مثل “BYO Model” السماح تلقائيًا بإرسال بيانات المشروع إلى مزود خارجي. للمكوّنات في هذا المستودع حدود تشغيل ومزودات مختلفة؛ راجع وثائق المكوّن المحدد ولا تفترض أن سياسة أحدها تنطبق على الآخر.

## التحقق من cherry-pick

نجاح `cherry-pick` يعني أن Git طبّق التغيير، لا أن النتيجة مطابقة للشجرة المقصودة. عندما يكون المطلوب إعادة إنتاج الشجرة نفسها، افحص commit المصدر ووالده أولًا، ثم قارن الشجرتين بعد التطبيق:

```bash
source_commit="FULL_OR_ABBREVIATED_COMMIT_SHA"
git show --no-patch --format='commit %H%nparent %P%nsubject %s' "$source_commit"
git rev-parse HEAD^{tree}
git rev-parse "${source_commit}^{tree}"
test "$(git rev-parse HEAD^{tree})" = \
     "$(git rev-parse "${source_commit}^{tree}")"
```

إذا اختلفت الشجرتان، فتوقف وافحص الفرق والوالد والسياق؛ لا تعتبر خلوّ `cherry-pick` من التعارضات دليلًا على التطابق. قد لا يُتوقع تطابق الشجرتين إذا كان أساس الدمج مختلفًا؛ عندئذٍ يجب فحص الفرق الناتج وشرح الاختلاف بدل الادعاء بالتطابق.

## إثبات حالة الـPR

وجود الفرع يثبت أن العمل محفوظ، لا أنه وصل. وعندما يوجد pull request فإنه يفتح سؤالًا ثانيًا: ما مصيره النهائي؟ سجّل حينها:

- [ ] رقم الـPR
- [ ] حالة الـPR: `OPEN` أو `CLOSED` أو `MERGED`
- [ ] SHA الـcommit الدمج إن كان `MERGED`
- [ ] عدد المراجعات
- [ ] عدد الموافقات

`MERGED` و`CLOSED` حالتان مختلفتان، وكلتاهما لا تدلّان على وجود مراجعة. تُقرأ هذه القيم من الـPR نفسه، لا من نجاح `git push` ولا من الحوار.

## إغلاق الفرع

الـPR المُدموج لا يُغلق فرعًا. بعد تسجيل حالة الـPR يُطرح سؤال ثالث: هل يبقى الفرع، وماذا يضيف؟

أرقام `compare` (`ahead_by`/`behind_by`) لا تصلح حكمًا هنا: إنها تعدّ انحراف التاريخ، لا فقدان المحتوى. عند الدمج بـ commit دمج حقيقي (`parents=2`) يبقى رأس الفرع وصولًا من `main` فيصبح عدّه الإضافي صفرًا؛ أما عند الدمج بـ squash (`parents=1`) فإن رأس الـPR يفقد وصوليته دائمًا، فيتأخّر الفرع بعدد كوميتاته مهما كان محتواه مُدمَجًا بالكامل. لذلك يُقرأ عدد الوالدين أولًا، ثم يُقارَن المحتوى نفسه: شجرة رأس الفرع مقابل شجرة كوميت الدمج في `main`؛ التطابق الشجري هو الدليل، والتباين في العدّ ليس.

```bash
git fetch origin main
head="$(git rev-parse origin/"$branch")"
main="$(git rev-parse origin/main)"
if git merge-base --is-ancestor "$head" "$main"; then
  echo "contained: the branch head is reachable from main"
elif test "$(git rev-parse "$head^{tree}")" = \
          "$(git rev-parse "$(gh pr view "$pr" --json mergeCommit --jq .mergeCommit.oid)"^{tree})"; then
  echo "squash-merged: content merged, branch head not reachable"
else
  echo "not merged: record the delta as an open item"
fi
```

- **الفرع لا يضيف شيئًا** (أحد الفرعين الأولين): يُحذف صراحةً، ويُرقَّم رأسه في السجل قبل الحذف؛ الاسترجاع ممكن من صفحة الـPR المدموج (`Restore branch`) أو بدفع ذلك الـSHA.
- **الفرع يضيف شيئًا**: يبقى، ويُسجَّل ما يضيفه بندًا معلّقًا. لا يُترك صامتًا: فرع معلّق بلا قرار ضجيج، وفرع معلّق بسبب عمل غير مدموج إشارة.
- **فرع بلا PR** لا يثبت إلا وجود عمل؛ قراره (حذف، أرشفة، أو فتح PR) يبقى قرارًا بشريًا.

## قائمة إغلاق الجلسة

- [ ] فُحص diff الفعلي، بما في ذلك الملفات الجديدة، وعُرفت الملفات التي تغيرت.
- [ ] نجحت الاختبارات المناسبة؛ سُجّلت أوامر الاختبار ونتائجها، ووُسمت أي اختبارات لم تُشغّل بوضوح.
- [ ] تعكس الوثائق ووصف PR/ChangeLog التغييرات والاختبارات الفعلية فقط.
- [ ] أُنشئ commit للعمل المقصود.
- [ ] اكتمل push إلى الفرع البعيد المقصود.
- [ ] نُفّذ fetch للفرع البعيد قبل التحقق من SHA.
- [ ] تطابق `HEAD` المحلي مع رأس الفرع البعيد المتوقع.
- [ ] حُسِم مصير الفرع بعد الـmerge: حُذف بعد إثبات الاحتواء، أو تُرِك مع سطر يوضح ما يضيفه فوق `main`.
- [ ] فُحص عدد والدي كوميت الدمج قبل قراءة أي عدّد `compare`؛ لا يُستنتج «عمل مفقود» من `behind_by` وحده.

بعد push، حدّث مرجع التتبع أولًا ثم قارن SHA. استخدم اسم الفرع الحالي والـremote الذي دُفع إليه العمل؛ المثال التالي يفترض أن اسمه `origin`:

```bash
branch="$(git branch --show-current)"
test -n "$branch" || { echo "Detached HEAD: select the intended branch." >&2; exit 1; }
git fetch origin "$branch"
test "$(git rev-parse HEAD)" = \
     "$(git rev-parse "origin/$branch")"
```

لا تُغلق الجلسة على أساس نجاح `git push` وحده. إذا فشل التحقق، أو لم يتطابق SHA، عالج حالة الفرع أو اذكر بوضوح أن التسليم لم يكتمل بعد.
