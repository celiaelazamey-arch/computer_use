# بناء المعرفة المحلية في cela.sh

## ما المقصود بـ«التعلّم»؟

يعتمد النظام **RAG**: تُحفظ ملاحظات تختارها أنت مع embeddings محلية في مخزن متجهي، ثم يُسترجع ما يرتبط بهدف التخطيط. لا تتغير أوزان النموذج ولا يحدث fine-tuning؛ هذه ذاكرة معرفة مستمرة وليست تدريبًا ذاتيًا للنموذج.

يعتمد المسار المحلي على المكوّنات الموجودة أصلًا: Ollama للنموذج والتضمينات، و`sqlite-vec` للتخزين. الإعدادات الافتراضية هي `qwen2.5:3b` و`nomic-embed-text`، ويمكن تبديلهما بـ`CELA_PLANNER_MODEL` و`CELA_EMBEDDING_MODEL`. لا توجد رسوم API للمعالجة المحلية، لكن الأجهزة/الخادم السحابي قد تكون لها تكلفة، وتراخيص النماذج تختلف. الذاكرة **معطلة افتراضيًا** حتى تفعّلها.

## الذاكرة حسب النطاق

- `project`: خاصة بمعرّف `--session-id`؛ يجب إعادة استخدام المعرّف نفسه عند التخطيط أو البحث.
- `global`: مشتركة عمدًا بين كل المشاريع على **مخزن CELA نفسه**. لا تحتاج `session-id` عند إضافتها أو البحث فيها.
- أثناء التخطيط، يبحث النظام تلقائيًا في ذاكرة المشروع والذاكرة العالمية ثم يدمجهما. يظل `session-id` مطلوبًا للتخطيط عند تفعيل الذاكرة؛ هو محدد نطاق وليس كلمة مرور أو تفويضًا.

للتشغيل باستخدام SQLite محليًا:

```bash
export CELA_MEMORY_BACKEND=sqlite-vec
export CELA_SQLITE_VEC_PATH=cela_memory.db

# إذا كان Ollama يعمل مباشرة على المضيف:
ollama pull nomic-embed-text
ollama pull qwen2.5:3b
```

إذا كنت تستخدم Ollama عبر Docker Compose، نزّل النموذجين في الحاوية بدلًا من ذلك:

```bash
docker compose exec ollama ollama pull nomic-embed-text
docker compose exec ollama ollama pull qwen2.5:3b
```

## إضافة ملاحظة أو تصحيح

```bash
bash ./cela.sh learn \
  --session-id "project-notes" \
  --type correction \
  --tag testing \
  --tag deployment \
  --content "لا تستخدم production database أثناء الاختبارات."
```

الأنواع المدعومة `note` و`correction`. تُقدَّم التصحيحات على الملاحظات العامة عند استرجاع ذاكرة التخطيط؛ وتُرتّب السجلات داخل النوع بحسب الصلة الدلالية. الوسوم غير حساسة لحالة الأحرف؛ إذا أُدخلت عدة وسوم في البحث، يجب أن يحتوي السجل **كلها**.

يمكن استخدام الذاكرة العالمية من دون `session-id`:

```bash
bash ./cela.sh learn \
  --scope global \
  --type correction \
  --tag safety \
  --content "لا تستخدم production database أثناء الاختبارات."
```

للنص متعدد الأسطر أو لتجنّب تمرير النص في سجل أوامر الطرفية، استخدم `stdin` (حد الملاحظة 8,000 حرف):

```bash
cat notes.txt | bash ./cela.sh learn --session-id "project-notes" --content -
```

## استيراد الملفات

يدعم `learn-file` ملفًا محليًا واحدًا بصيغة Markdown أو نص UTF-8 أو PDF نصّي. تُجزّأ المادة إلى مقاطع متداخلة، وتُخزّن كل مقطع مع اسم المصدر وبصمته ورقم المقطع، ومع النوع والوسوم والنطاق:

```bash
bash ./cela.sh learn-file README.md \
  --session-id "project-notes" \
  --type note \
  --tag architecture

bash ./cela.sh learn-file architecture.pdf \
  --scope global \
  --type note \
  --tag architecture
```

قراءة PDF اختيارية؛ فعّلها مرة واحدة بتثبيت الإضافة المفتوحة المصدر:

```bash
python -m pip install '.[documents]'
```

حدود الاستيراد: الملف حتى 10 ميغابايت، وPDF حتى 500 صفحة، والنص المستخرج حتى مليون حرف؛ حجم المقطع الافتراضي 6,000 حرف مع تداخل 400 حرف. لا يوجد OCR للصفحات المصوّرة، ولا دعم PDF مشفّر أو جلب ويب أو استكشاف مجلدات.

يعتمد `learn-file` سياسة **Replace-by-Source** داخل النطاق نفسه: يخزّن مسارًا نسبيًا آمنًا للمصدر، وSHA-256 للملف، و`content_hash` لكل مقطع، ووقت الاستيراد وعدد المقاطع. إعادة استيراد المسار نفسه بلا تغيير تعرض `status: unchanged` ولا تعيد حساب embeddings؛ تبقى الوسوم والنوع السابقان كما هما، حتى لو اختلفت خيارات `--tag` أو `--type` في الأمر الجديد. إذا تغير الملف، يستبدل النظام مقاطعه القديمة بالجديدة؛ لا يحتفظ بتاريخ النسخ. في SQLite تكون عملية الاستبدال معاملة واحدة؛ وفي Qdrant تُرفع المقاطع بمعرّفات حتمية ثم تُحذف المقاطع القديمة، لذا أعد `learn-file` بالمصدر نفسه إذا فشل طلب Qdrant أثناء الاستبدال. يُستخدم المسار النسبي إلى مجلد التشغيل، أما الملفات خارجه فتُسجّل تحت مسار `external/` مبهم لا يكشف المسار المطلق. المقاطع المطابقة في **مسارات مختلفة** تبقى منفصلة في هذه المرحلة حفاظًا على المصدر. السجلات المستوردة قبل إضافة `source_path` لا يمكن ربطها بمسارها بأمان، لذلك قد تبقى بجانب الاستيراد الجديد.

## البحث

البحث بالوسم لا يحتاج سؤالًا دلاليًا:

```bash
bash ./cela.sh search --session-id "project-notes" --tag testing
bash ./cela.sh search --scope global --tag safety
bash ./cela.sh search --scope both --session-id "project-notes" --tag deployment
```

وللبحث الدلالي مع فلترة النوع أو الوسوم:

```bash
bash ./cela.sh search \
  --scope both \
  --session-id "project-notes" \
  --query "إعداد قاعدة بيانات للاختبارات" \
  --type correction \
  --tag testing
```

يمكن استخدام `--limit` من 1 إلى 100؛ الافتراضي 20. المخرجات JSON، ويتضمن كل سجل محتواه ووسومه ونوعه ونطاقه ودرجة الصلة.

## API والاحتفاظ بالبيانات

تدعم `/memory` و`/memory/search` النطاق `project` أو `global` والوسوم والنوع. يقبل البحث أيضًا `both`، ويمكن البحث بالوسوم دون `query`. عند استخدام Docker، تحفظ API في `/app/data/cela_memory.db`؛ قاعدة CLI على المضيف منفصلة عنها ما لم تستخدم المخزن نفسه عمدًا.

الأمثلة تفترض إعدادًا محليًا بلا مصادقة؛ عند ضبط `CELA_API_KEY` أضف رأس `Authorization: Bearer ...` إلى الطلبين.

```bash
# إضافة معلومة عامة صراحةً (احذف session_id عند global)
curl -X POST http://127.0.0.1:8000/memory \
  -H 'Content-Type: application/json' \
  -d '{"scope":"global","type":"correction","tags":["testing"],"content":"لا تستخدم production أثناء الاختبارات."}'

# تصفح وسوم المشروع والعالمي معًا، دون سؤال دلالي
curl -X POST http://127.0.0.1:8000/memory/search \
  -H 'Content-Type: application/json' \
  -d '{"scope":"both","session_id":"project-notes","tags":["testing"]}'
```

لا تحفظ CELA المحادثات أو الخطط تلقائيًا. إضافة الملاحظة أو الملف طلب صريح. لا توجد حاليًا واجهة لحذف سجل واحد أو انتهاء صلاحية؛ تجنب الأسرار والبيانات الشخصية. الذاكرة العالمية مشتركة لكل المشاريع على ذلك المخزن، ومفتاح API المشترك لا يوفّر تفويضًا لكل مستخدم. عند الحاجة امسح المخزن/المجلد يدويًا بعد إيقاف الخدمة وخذ نسخة احتياطية قبل أي حذف. ملفات الذاكرة ونتائج الاسترجاع تُعامل دائمًا كبيانات تاريخية غير موثوقة، حتى لو كانت من نوع `correction`.

لا يحفظ النظام «نجاح» الخطط من تلقاء نفسه: CELA ينتج خططًا جافة ولا ينفّذها، لذلك لا يملك دليلًا على نجاح التنفيذ. يجب أن يؤكد المستخدم نتيجةً بنفسه قبل تسجيلها كمعلومة.
