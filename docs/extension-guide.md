# دليل توسعة مستودع CELA

**الغرض:** أن تبقى كل توسعة إضافةً لا جراحة، وأن يُكتشف أي كسر آليًا قبل أن يصل `main`.

**القاعدة الحاكمة:** المستودع لا يمنعك من توسعته؛ يمنعك من توسعته **بصمت**. كل عقد عام مُثبَّت في لقطة قابلة للمراجعة، وكل سلوك أمني مُثبَّت في اختبار، وكل إضافة جديدة تمرّ من البوابة نفسها التي مرّت منها الكود القائم.

## طبقات الحماية الأربع

| الطبقة                | أين                                                                                     | ماذا تمنع                                                                   |
| --------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 1. عقود قابلة للإضافة | `src/cela_sh/memory/registry.py`، `factory.py`                                          | تعديل ملفات قائمة لإضافة قدرة جديدة                                         |
| 2. كواشف كسر آلية     | `tools/api_surface.py`، `tests/snapshots/api_surface.json`، `tests/test_api_surface.py` | حذف أو إعادة تسمية أو تغيير توقيع أو علم/أمر CLI أو كود خروج أو مسار Worker |
| 3. عقود سلوكية مشتركة | `tests/contract_memory_store.py`، `tests/test_extension_contracts.py`                   | مكوّن جديد لا يلتزم بقواعد العزل والتحقق نفسها                              |
| 4. بوابة واحدة        | `bash ./cela.sh preflight` وCI                                                          | دفع تغيير لم يُفحص                                                          |

## قبل أن تبدأ

### 1. ثبّت خط أساس أخضر

لا تبدأ من حالة لا تعرفها. نفّذ:

```bash
bash ./cela.sh install-all
bash ./cela.sh preflight
```

يجب أن تنتهي بـ `preflight passed.`. إن فشلت قبل تغييرك، فأصلح الأساس أولًا أو ابدأ من commit نظيف؛ وإلا فلن تعرف من كسر ماذا.

### 2. حدّد أي مكوّن تلمس

| تريد إضافة…                      | المكوّن                | الدليل       |
| -------------------------------- | ---------------------- | ------------ |
| ذاكرة دائمة جديدة، استرجاع مختلف | `cela.sh` (Python)     | الوصفة 1     |
| نموذج تخطيط محلي آخر             | `cela.sh` (Python)     | الوصفة 2     |
| فعل جديد، قاعدة مخاطر جديدة      | `cela.sh` (Python)     | الوصفات 3 و4 |
| مسار API أو صفحة                 | `ccelia2027/` (Worker) | الوصفة 6     |
| متغير إعداد، خدمة محلية          | كلاهما                 | الوصفات 7 و8 |

### 3. اسأل سؤال نموذج التهديد

قبل أي كود: **هل تضيف هذه التوسعة قدرة تنفيذ، أو تصل إلى شبكة غير loopback، أو تنقل بيانات بين المكوّنين، أو تستقبل سرًّا جديدًا؟**

- إن كان الجواب لا → تابع الوصفة المناسبة.
- إن كان نعم → توقّف واقرأ «ما لا يجوز أبدًا» ثم افتح issue للنقاش. هذا ليس إجراءً شكليًا: كل من `cela.sh` و`ccelia2027/` مبني على وعد «لا تنفيذ»، وأي وصلة تنفيذية تغيّر نموذج التهديد للمستودع كله.

## الوصفة 1: إضافة مخزن ذاكرة جديد

هذه هي التوسعة الأكثر أمانًا في المستودع، لأنها لا تلمس أي ملف قائم.

**الخطوة 1** — أنشئ ملفًا جديدًا `src/cela_sh/memory/example_store.py` وطبّق العقد:

```python
from typing import Any

from .base import MemoryStore


class ExampleMemoryStore(MemoryStore):
    def __init__(self, timeout: tuple[float, float] = (3.05, 60.0)) -> None:
        self.timeout = timeout

    def add_memory(self, session_id: str, content: str, metadata: dict[str, Any] | None = None) -> bool:
        ...

    def search_memory(self, query: str, session_id: str, limit: int = 3) -> list[dict[str, Any]]:
        ...
```

القواعد التي يفرضها `tests/contract_memory_store.py` وليست اختيارية:

- رفض `session_id` الفارغ، و`content` الفارغ أو الأطول من 8000 حرف، و`metadata` غير القابل للترميز JSON.
- **عزل الجلسات:** لا يُعاد أبدًا سجل جلسة أخرى، حتى لو أعاده الخادم نفسه.
- شكل النتيجة ثابت: `{"session_id", "content", "metadata", "score"}` مع `score` عددًا حقيقيًا منتهيًا.
- النتائج **نسخ** لا حالة مشتركة: تعديل نتيجة لا يغيّر المخزن، ونسخ `metadata` عند الكتابة وعند القراءة.
- لا شبكة ولا اعتمادية جديدة دون نقاش مسبق.

`list_memory(session_id, limit, *, tags, memory_type)` و`replace_source(session_id, source_path, source_hash, chunks)` قدرتان اختياريتان في `MemoryStore` للحفاظ على توافق المخازن القديمة. إذا كان الـ backend الجديد سيستخدم البحث دون `query`، فعليه تنفيذ `list_memory`. وإذا كان سيُفعّل `learn-file`، فعليه تنفيذ `replace_source` كعملية قابلة للتكرار بأمان: التحقق من الدفعة كاملة، تخطي بصمة ملف مطابقة، واستبدال مقاطع المصدر عند اختلافها. استخدم معاملة ذرية إن دعمها المخزن؛ أما المخازن الموزعة فعليها تصميم upsert/تنظيف يسمح بإعادة المحاولة والتقارب إلى نسخة واحدة. وإلا سيعيد العقد خطأً واضحًا بدل الادعاء بأنه استبدل المصدر.

**الخطوة 2** — صدّر الاسم في `src/cela_sh/memory/__init__.py` (إضافة إلى `__all__`، لا تعديل ما هو موجود).

**الخطوة 3** — سجّل الـ backend في `factory.py` ببنّاء واحد:

```python
def _build_example_store(config: Settings, timeout: tuple[float, float]) -> ExampleMemoryStore:
    return ExampleMemoryStore(timeout=timeout)


register_memory_backend("example", _build_example_store)
```

لا تعدّل `create_planner` ولا `Settings`. التسجيل وحده يكفي: `CELA_MEMORY_BACKEND=example` يصبح قيمة صالحة، و`create_planner` يحقن المخزن تلقائيًا.

**الخطوة 4** — ثبّت العقد على مخزنك في `tests/test_extension_contracts.py`:

```python
class ExampleMemoryStoreContractTests(MemoryStoreContract, unittest.TestCase):
    def make_store(self):
        return ExampleMemoryStore()
```

وأضف اسمه إلى `COVERED_BACKENDS`. إن نسيت، يفشل `test_every_registered_backend_is_covered_by_a_contract_suite` ويخبرك بالاسم الناقص.

**الخطوة 5** — وفّر بديل اختبار غير متصل في `tests/fakes.py` إن كان مخزنك يتحدث إلى خدمة، كما يفعل `FakeQdrantSession`. الاختبار الذي يحتاج خدمة حقيقية لا يُشغَّل في CI، أي أنه لا يحمي شيئًا.

**الخطوة 6** — سجّل اللقطة وراجع الفرق:

```bash
bash ./cela.sh api-surface --update
git diff tests/snapshots/api_surface.json
```

**الخطوة 7** — حدّث `.env.example` و`docs/protocol.md` و`README.md` بقيمة `CELA_MEMORY_BACKEND` الجديدة.

## الوصفة 2: إضافة مزوّد تخطيط محلي آخر

واجهة `Planner` المجردة وسجلّ المزودين في `src/cela_sh/planner/registry.py` يعملان بالطريقة نفسها التي يعمل بها سجلّ الذاكرة:

1. أنشئ صنفًا جديدًا يرث `Planner` ويطبّق `generate_plan(goal, screen_context, session_id) -> Plan` مع استخدام `_prepare_request` و`_finalize_plan` لضمان التحقق الصارم وتطبيق السياسة.
2. سجّل المزوّد في `factory.py` (أو وحدة التوسعة) عبر `register_planner_provider("example-local", _build_example_planner)`. بذلك تصبح `CELA_PLANNER_PROVIDER=example-local` قيمة صالحة تلقائيًا، ويحقن `create_planner` مخزن الذاكرة المختار دون تعديل `settings.py` أو `factory.py`.
3. أضف صنف اختبار يرث `PlannerContract` في `tests/test_extension_contracts.py` وأضف اسم المزوّد إلى `COVERED_PLANNER_PROVIDERS`.
4. ثبّت في الاختبارات أن المزوّد يعيد `Plan` تحمل `dry_run=True` و`execution_enabled=False`، ويرفض أي مخطط غير مطابق بدل إرجاع خطة بديلة.
5. سجّل اللقطة عبر `bash ./cela.sh api-surface --update`.

لا تحذف `OllamaPlanner` ولا تغيّر أسماء أخطائه؛ الـ CLI يربط كل خطأ بكود خروج مُثبَّت في `EXIT_CODES`.

## الوصفة 3: إضافة فعل جديد إلى `Action`

**تحذير:** هذه التوسعة توسّع ما قد يقترحه النموذج، لذا هي تغيير في نموذج التهديد وليست إضافة روتينية.

1. حدّد أولًا لماذا لا يغطي فعل قائم الحالة (`OBSERVE`, `ASK_USER`, `WAIT` تغطي أغلب ما يُطلب).
2. أضف العضو إلى `Action` في `src/cela_sh/planner/models.py`.
3. أضف قاعدة سياسة صريحة له في `src/cela_sh/planner/policy.py`: إما `low` مع سبب موثق، أو `requires_confirmation`، أو `blocked`. الفعل دون قاعدة سياسة يُعامل كـ `low` افتراضيًا، وهذا غير مقبول.
4. أضف اختبارات سياسة للحالة الجديدة ولحالة الرفض.
5. حدّث `docs/protocol.md` (قائمة الأفعال) و`SYSTEM_PROMPT` في `planner/client.py` إن تغيّر معنى `target` أو `value`.
6. سجّل اللقطة: `test_the_snapshot_locks_the_action_allowlist` سيفشل حتى تقرّ التغيير صراحةً في طلب السحب.

## الوصفة 4: إضافة قاعدة سياسة

`policy.py` تصنيف قواعدي مستقل عن النموذج. الإضافة الآمنة:

- أضف النمط إلى `SENSITIVE_TERMS` أو `SHELL_COMMAND_TERMS` أو أنشئ نمطًا جديدًا باسم واضح.
- اجعل القاعدة **تضيّق** لا توسّع: لا تُنزل خطوة من `blocked` إلى `low` دون مراجعة أمنية.
- أضف اختبارًا للحالة الموجبة والحالة السالبة (نص يشبه ولا يجب أن يُلتقط).
- القواعد العربية والإنجليزية معًا؛ المستودع ثنائي اللغة.

## الوصفة 5: إضافة علم أو أمر CLI جديد

1. للعلم في وضع التخطيط، أضف `parser.add_argument(...)` في `build_parser()` بقيمة افتراضية تحفظ الاستدعاءات القديمة. لوضع مستقل، أنشئ parser واضحًا، وجّه الأمر من `cli.main()` بتحميل كسول، وسجّل أعلامه في `cli_subcommands` عبر `tools/api_surface.py`.
2. إن أضفت فشلًا جديدًا، أضف كود الخطأ إلى `EXIT_CODES` في `cli.py` وارمِ الاستثناء المناسب. **لا تعدّل كود خروج قائمًا**؛ السكربتات تعتمد عليه.
3. أضف اختبارًا يثبت السلوك والحدود وأن stdout/stderr يحافظان على JSON المتفق عليه.
4. حدّث `docs/protocol.md` وجدول الأكواد إذا تغيّرا.
5. سجّل اللقطة.

## الوصفة 6: إضافة مسار إلى Worker

الـ Worker في `ccelia2027/src/index.js` يستخدم `createWorker(launchBrowser)` كنقطة حقن، وسلسلة مسارات صريحة. القواعد:

1. المسار الجديد يُضاف إلى سلسلة `url.pathname` **قبل** الـ catch-all `url.pathname.startsWith("/api/")`.
2. أي مسار يغيّر حالة أو يستهلك ميزانية يحتاج جلسة صالحة (`validSession`) ومفتاح `rateKey` وحدًّا في `DailyBudget`.
3. لا تضف طريقة HTTP جديدة إلى جلب الصفحات: القراءة تبقى `GET`/`HEAD` من الأصل نفسه وعبر HTTPS عام فقط.
4. أضف اختبارًا في `ccelia2027/tests/worker.test.js` للحالة السعيدة **وللحالة المرفوضة** (بلا جلسة، بلا أصل مطابق، بلا ميزانية).
5. شغّل `npm run lint && npm run format:check && npm test && npm run build` من `ccelia2027/`.
6. سجّل اللقطة: المسار الجديد يظهر في `worker.routes`، ويجب أن يُراجَع في طلب السحب.

## الوصفة 7: إضافة متغير إعداد جديد

1. أضف الحقل إلى `Settings` **بقيمة افتراضية** تحفظ السلوك الحالي؛ ثم اقرأه في `from_env()`.
2. أضف تحققه في `__post_init__` وارمِ `ConfigurationError` برسالة تسمّي المتغير.
3. أضف المتغير إلى `.env.example` مع قيمته الافتراضية، وإلى `docs/protocol.md`.
4. أضف اختبارًا في `tests/test_settings.py` للحالة الصالحة والحالة المرفوضة.
5. لا تحمّل ملف `.env` تلقائيًا؛ النظام يقرأ بيئة العملية فقط، وهذا قرار مقصود.
6. لا تضع سرًّا في `.env.example` أو في أي ملف متتبع.
7. سجّل اللقطة (توقيع `Settings.__init__` جزء من العقد).

## الوصفة 8: إضافة خدمة محلية إلى Compose

1. أضف الخدمة إلى `docker-compose.yml` تحت `profiles` إن لم تكن مطلوبة للمسار الافتراضي.
2. اربط المنفذ على `127.0.0.1` فقط: `"127.0.0.1:PORT:PORT"`. لا تنشر منفذًا على الإنترنت.
3. أضف وحدة تخزين مسماة إن كانت الخدمة تحفظ حالة، ولا تستخدم `docker compose down -v` في أي سكربت.
4. أضف أمر تشغيل/إيقاف في `cela.sh` يفحص وجود `docker` أولًا ويخرج بالرمز 2 مع رسالة واضحة إن غاب.
5. حدّث `README.md` و`docs/system-architecture.md`.
6. إن كانت الخدمة اختيارية، اجعل فحصها الحي منفصلًا (بنمط `probe-memory`) ولا تدخله في CI.

## ما لا يجوز أبدًا

هذه ليست تفضيلات؛ كل واحدة منها مُثبَّتة في اختبار، وكسرها يُفشل CI:

- **لا تنفيذ.** `dry_run` يبقى `Literal[True]` و`execution_enabled` يبقى `Literal[False]`. لا طبقة إدراك، لا التقاط شاشة، لا نقر، لا كتابة، لا أوامر نظام.
- **لا أوامر نظام في الخطة.** أي خطوة تستهدف shell أو تحمل أمر نظام تُصنَّف `blocked`.
- **لا توسيع اتصال Ollama بلا مراجعة.** loopback عبر HTTP هو الافتراضي. الاستثناء الموثق `CELA_ALLOW_OLLAMA_CONTAINER_HOST=true` يسمح باسم `ollama` فقط لشبكة Docker الموثوقة؛ أي اسم أو شبكة أخرى مرفوضان. redirects معطلة و`trust_env=False` دائمًا.
- **لا Qdrant بعيد بلا HTTPS ومفتاح.**
- **لا دمج بين المكوّنين.** Worker لا يستدعي Python، وPython لا يستخدم أسرار Cloudflare. أي وصلة تحتاج عقد بيانات مشتركًا ومصادقة وحدود حفظ واختبارات رفض وتكلفة موثقة.
- **لا حذف اسم عام** من `cela_sh.__all__` أو كسر معاملات توقيع قائم أو تغيير كود خروج. معاملات keyword اختيارية جديدة بقيم افتراضية تحفظ السلوك تحتاج اختبارات توافق وتوثيقًا ومراجعة فرق اللقطة صراحةً.
- **لا كتابة ذاكرة تلقائية.** `learn` و`add_memory` و`POST /memory` طلبات صريحة؛ لا تجمع المحادثات أو الخطط تلقائيًا.
- **لا سرّ في المستودع**، ولا مخرجات مولدة، ولا بيانات شخصية.
- **لا تجاوز الحارس بحذف اختبار.** إن كان الاختبار يعيقك، فهو يخبرك بشيء عن التصميم.

## عندما يكتشف الحارس كسرًا

| الرسالة                                      | المعنى                         | التصرف                                                       |
| -------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| `REMOVED public name: X`                     | حُذف اسم عام                   | أعده، أو وفّر alias مع دورية إهمال موثقة                     |
| `CHANGED public name: X`                     | تغيّر توقيع أو حقل أو عضو enum | إن كان مقصودًا: وثّقه ككسر توافق وقدّم بديلًا؛ وإلا فالتراجع |
| `ADDED public name: X`                       | إضافة جديدة                    | راجع الفرق ثم `bash ./cela.sh api-surface --update`          |
| `REMOVED CLI flag` / `CHANGED exit code`     | كسر في عقد السكربتات           | لا يمرّ؛ أعِد القيمة القديمة                                 |
| `ADDED Worker route`                         | مسار جديد                      | راجع المصادقة والحدود والميزانية ثم سجّل اللقطة              |
| `Add a MemoryStoreContract suite for: [...]` | backend بلا عقد                | أضف صنف الاختبار كما في الوصفة 1                             |
| `Public contract surface drifted`            | الفرق الكامل                   | اقرأ كل سطر قبل `--update`                                   |

**لا تشغّل `--update` قبل أن تقرأ الفرق.** اللقطة توقيع، وليست ملفًا مولّدًا يُتجاهل.

## قائمة ما قبل طلب السحب

```bash
bash ./cela.sh preflight          # الاختبارات + اللقطة + بناء الحزمة + Worker
```

ثم تأكد يدويًا:

- [ ] `git diff tests/snapshots/api_surface.json` مقصود ومشروح في وصف الطلب.
- [ ] كل سلوك جديد له اختبار، وكل رفض جديد له اختبار رفض.
- [ ] `.env.example` و`docs/protocol.md` و`README.md` محدّثة إن تغيّر الإعداد أو البروتوكول.
- [ ] `CHANGELOG.md` يصف التغيير بلغة المستخدم لا بلغة الملف، تحت إصدار واحد حالي.
- [ ] لا اعتمادية تشغيلية جديدة دون نقاش؛ الاعتماديات الجديدة تُثبَّت بنطاق إصدار وتُفحص بـ `npm audit` وDependabot.
- [ ] لا سرّ في `git diff`.
- [ ] إن أضفت فحصًا حيًا (يتصل بخدمة حقيقية)، فهو منفصل عن CI وموثق في `docs/phase-1-milestone.md`.

## التراجع

كل توسعة يجب أن تكون قابلة للتراجع دون فقدان بيانات:

- **الكود:** التراجع هو `git revert` لـ commit واحد. اجعل كل إضافة commit مستقلًا حتى يبقى هذا صحيحًا.
- **الإعداد:** كل متغير جديد له قيمة افتراضية تحفظ السلوك القديم، فإلغاء تفعيله يكفي للتراجع.
- **الذاكرة:** الـ backends معطلة افتراضيًا (`CELA_MEMORY_BACKEND=disabled`)، والتراجع هو إبقاءها معطلة. لا تحذف وحدات التخزين؛ `docker compose down -v` يدمّر النماذج والذاكرة.
- **الـ Worker:** النشر يدوي ومنفصل (`npm run deploy`)، و`npm run build` فحص جاف فقط. التراجع هو نشر الإصدار السابق من Cloudflare.
