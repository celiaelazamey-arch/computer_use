# معمارية مستودع CELA

## هوية النظام

هذا المستودع منتج واحد بواجهتي تشغيل منفصلتين. وحدة الصيانة مشتركة، أما مزوّد النموذج وحدود البيانات والتنفيذ فتبقى معزولة لكل مكوّن. لا توجد حاليًا وصلة وقت تشغيل بين Python وWorker.

```text
مستودع CELA
├── cela.sh / Python
│   الهدف + سياق نصي → Ollama محلي → تحقق Pydantic وسياسة مخاطر → خطة JSON جافة
└── ccelia2027 / Cloudflare Worker
    المهمة → Workers AI → تحقق الخطة وربط الوجهة → فحص DNS عام
    → Browser Run للقراءة فقط → أدلة الصفحة وملخص المهمة

الطبقة المشتركة: مدخل المستودع، CI، CodeQL، Dependabot، الوثائق
```

## المكوّن المحلي

الحزمة `cela-sh` تعمل عبر `bash ./cela.sh` أو `python -m cela_sh` أو API اختيارية. تستخدم Ollama على loopback افتراضيًا، أو اسم خدمة Docker `ollama` عند السماح الصريح؛ وتسمح بـsqlite-vec الرسمي أو Qdrant مع عزل الجلسات. المخطط والسياسة يصنفان الأفعال، لكن لا توجد طبقة تنفيذ أو تحكم بالواجهة. كل خطة تحمل `dry_run=true` و`execution_enabled=false`؛ و`ready` لا يعني إذنًا بالفعل.

الاختبارات في `tests/` تستخدم embeddings حتمية مع vec0 الحقيقي، وبدائل HTTP؛ لا تحتاج Ollama أو Qdrant. الصورة متعددة المراحل تشغّل API كمستخدم غير root، وتنشرها على loopback فقط دون مصادقة بعد؛ التفاصيل في [دليل Docker](docker-deployment.md). `bash ./cela.sh probe` و`probe-memory` فحوص حية اختيارية ويجب تشغيلهما صراحةً على الجهاز المقصود.

## المكوّن المستضاف

التطبيق في `ccelia2027/` يخدم واجهة عربية وAPI من Worker واحد. يستخدم Workers AI للتخطيط والتلخيص، وBrowser Run لجلسة Playwright قصيرة ومعزولة. يقبل فقط التنقل إلى HTTPS عام صرّح به المستخدم والقراءة عبر GET/HEAD من الأصل نفسه. يرفض الوجهات غير العامة والخطط غير المطابقة، ولا يدعم تسجيل الدخول أو الضغط أو الكتابة أو تغيير البيانات.

اختبارات Worker تستخدم محاكاة ولا تثبت صحة حساب Cloudflare أو استهلاكًا حيًا. `npm run build` هو Wrangler dry-run فقط؛ `npm run deploy` نشر فعلي ولا يستخدم كفحص.

## حدود الثقة والبيانات

- Python لا يرسل بياناته إلى Worker، وWorker لا يتصل بخدمة Ollama المحلية.
- أسرار Cloudflare وبيانات التطبيق تخص GitHub Actions/Cloudflare فقط، ولا تدخل بيئة Python.
- نص الهدف والسياق والذاكرة غير موثوق. الخطة تحتاج تحققًا وقاعدة رفض مستقلة عن النموذج.
- SQLite/Qdrant يحتويان ذاكرة جلسة عند التفعيل والكتابة الصريحة فقط. Worker Durable Object يحتفظ بعدادات الاستخدام اليومية لا بنص المهام.
- اختبارات CI لا تشغّل Ollama أو Browser Run أو NVIDIA ولا تنشر الإنتاج.

## تشغيل وصيانة موحّدان

من جذر المستودع:

```bash
bash ./cela.sh install-all
bash ./cela.sh check-all
bash ./cela.sh worker-dev
```

`check-all` يشغّل اختبارات Python وبناء الحزمة، واختبارات Worker وLint والتنسيق وتدقيق npm وبناء Wrangler التجريبي. CI يشغّل فحوص Python وWorker في مهمتين متوازيتين، وفحصًا إضافيًا لبناء حاوية API وعمل vec0 وفحص الحياة دون نماذج حية. CodeQL يفحص JavaScript/Python، وDependabot يغطي pip وnpm وGitHub Actions. سير النشر منفصل ويدوي، ولا يعمل تلقائيًا عند push.

## طبقة حماية التوسعة

التوسعة مُتوقعة، أما الكسر الصامت فمرفوض. المستودع يثبّت عقودَه بثلاث آليات تعمل على كلا التطبيقين:

- **سجلات قابلة للإضافة:** مخازن الذاكرة تُسجَّل عبر `register_memory_backend` في `src/cela_sh/memory/registry.py`، فيصبح الـ backend الجديد قيمة صالحة لـ`CELA_MEMORY_BACKEND` دون تعديل `factory.py` أو `settings.py` أو CLI.
- **لقطة العقد العام:** `tools/api_surface.py` يلتقط الأسماء المصدَّرة والتواقيع وأعضاء `Action` وحقول النماذج وأعلام CLI وأكواد الخروج ومسارات Worker في `tests/snapshots/api_surface.json`. الحذف أو إعادة التسمية أو تغيير كود خروج يفشل CI؛ والإضافة تمرّ فقط بعد مراجعة الفرق وتسجيله صراحةً.
- **عقود سلوكية مشتركة:** `tests/contract_memory_store.py` مجموعة واحدة تُطبَّق على كل مخزن عبر بدائل غير متصلة في `tests/fakes.py`، فلا يُقاس backend جديد بقواعد أضعف من القائم.

`bash ./cela.sh preflight` يشغّل هذه الطبقة كاملة دون Docker أو شبكة أو نشر، وCI يشغّل الفحوص نفسها. الوصفات خطوة بخطوة في [دليل التوسعة](extension-guide.md).

## حدود الدمج مستقبلًا

لا تحوّل الخطط بين المخططين ولا تجعل Worker يستدعي Python أو العكس دون عقد بيانات مشترك، ومصادقة، وحدود حفظ/نقل البيانات، واختبارات رفض وتكلفة موثقة. أي وصلة تنفيذية تغيّر نموذج التهديد ويجب مراجعتها قبل إضافتها.
