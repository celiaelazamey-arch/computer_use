## CELA.sh 1.0.1

A security and documentation release. Planning behavior itself is unchanged: plans remain `dry_run=true` and `execution_enabled=false`, and there is no `/execute`.

> **Link notice:** every link in these notes points at `main`. They resolve only after [pull request #17](https://github.com/celiaelazamey-arch/computer_use/pull/17) is merged into `main` and the merge commit is tagged. Before the merge they return `404`.

### One reference for the error contract

**[docs/api-errors.md](https://github.com/celiaelazamey-arch/computer_use/blob/main/docs/api-errors.md)** was added as the single reference for the local API error contract. The two tables below **re-display** that page; they are not an independent copy. If they ever disagree, the page is right.

Every row in both tables was confirmed by running the application, not by reading the source alone.

#### Two response shapes, not one

This is the most important part of the release. The API returns **two different envelopes** depending on where the error originates:

| Envelope                   | Shape                                          | Source                                                                               |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| **A** — application errors | `{"error": {"code": "...", "message": "..."}}` | Known domain failures and unexpected exceptions; every `message` is a fixed sentence |
| **B** — framework errors   | `{"detail": ...}`                              | FastAPI/Pydantic request-body validation, 404, and 405                               |

Practical consequence: **inspect the envelope before assuming a `code`.** A `422` status alone is not enough — it has three different origins across the two envelopes.

#### Table A — application errors

| Status | `code`                     | Fixed `message`                                 | Path                        |
| -----: | -------------------------- | ----------------------------------------------- | --------------------------- |
|    409 | `memory_disabled`          | `Memory is disabled in this deployment.`        | `/memory`, `/memory/search` |
|    422 | `planner_validation_error` | `Planner input validation failed.`              | `/plan`                     |
|    422 | `memory_validation_error`  | `Invalid memory input.`                         | `/memory`                   |
|    422 | `memory_validation_error`  | `Invalid memory search input.`                  | `/memory/search`            |
|    500 | `planner_error`            | `An internal planner error occurred.`           | `/plan`                     |
|    500 | `internal_error`           | `Internal server error.`                        | any HTTP path               |
|    502 | `planner_response_error`   | `Planner service returned an invalid response.` | `/plan`                     |
|    503 | `planner_connection_error` | `Unable to connect to planner service.`         | `/plan`                     |
|    503 | `planner_memory_error`     | `Planner memory backend is unavailable.`        | `/plan`                     |
|    503 | `memory_store_error`       | `Memory store is unavailable.`                  | `/memory`, `/memory/search` |

`memory_validation_error` carries two different fixed sentences, one per path. The code is single; the message is not.

#### Table B — framework errors

| Status | Shape                                                   | Trigger                                                                           |
| -----: | ------------------------------------------------------- | --------------------------------------------------------------------------------- |
|    422 | `{"detail": [{"type", "loc", "msg", "input", "ctx"?}]}` | Missing or out-of-bounds field, invalid JSON, extra field, whitespace-only string |
|    404 | `{"detail": "Not Found"}`                               | Unknown path                                                                      |
|    405 | `{"detail": "Method Not Allowed"}`                      | Wrong method on an existing path                                                  |

`detail` messages are generated by Pydantic, not fixed sentences of ours; do not build logic on them. Depend on `type` and `loc` only.

### What changed in behavior

**Unexpected exceptions no longer leak.** Before this release, unhandled exceptions fell through to Starlette: either a plain-text body, or a registered handler that sends its response and then re-raises — which lets a test client or a debug server surface the original detail. `UnexpectedErrorMiddleware` now answers inside the request path itself:

```json
{ "error": { "code": "internal_error", "message": "Internal server error." } }
```

The guarantees, all of them tested:

- No original exception text, no exception class name, no `Traceback`, no internal file paths, no model names, no connection strings.
- The traceback is written to the server log (`cela_sh.server` at `ERROR`) exactly once per failure. Sanitizing relocates the detail; it does not hide it.
- If the response already started (`http.response.start` was sent) it is not replaced, because swapping the body after sending would corrupt the stream.
- Non-HTTP scopes (such as `lifespan`) pass through untouched.
- One failed request does not wedge the application: `/health` still returns `200` after a `500`.

### Remaining items in this release

- **Uniform system-command blocking:** `sudo`, privilege-escalation tools (`doas`, `pkexec`, `su -`), shell commands (`rm -rf`, `bash -c`, `powershell -`, `cmd /c`, `chmod`, `chown`), and shell targets (`terminal`, `PowerShell`, `الطرفية`, `سطر الأوامر`) are now blocked uniformly across all action types and in the goal text, returning `status: blocked` with explicit guidance to run the intended command manually in the user's own terminal.
- **Extensible planner contract:** the abstract `Planner` interface (`cela_sh.planner.base`) and the local provider registry (`register_planner_provider`, `build_planner`, `CELA_PLANNER_PROVIDER`) were extracted, with shared `PlannerContract` enforcement. `OllamaPlanner` remains the default strictly local provider.
- **Consequential verbs require confirmation:** send, submit, post, publish, upload, email, reply, share, message, order, checkout, subscribe, and their Arabic equivalents no longer return `ready` with `low` risk. Classification applies to the goal and to each step.
- **`ccelia2027`: each plan token executes once.** Replays return `409 plan_already_used` before any browser starts. Tokens issued before this change carry no `jti` and are rejected; during a short deploy window, holders of unexpired old-format tokens get a `400` and must create a new plan.

### Version inventory: six locations, not four

Bumping to `1.0.1` exposed that `CHANGELOG.md` documented only four locations while the version string actually lives in **six**. The two missing ones are not cosmetic:

- `src/cela_sh/server.py` — the `version=` passed to FastAPI, which is **published to callers** through `/openapi.json` and `/docs`. Bumping only the four documented files would have shipped a public OpenAPI contract advertising a stale version.
- `SECURITY.md` — the supported-versions table.

`tests/test_version_consistency.py` was added to fail the build on any drift between the six locations and the newest `CHANGELOG.md` heading. The guard was checked during development by mutating each of the seven anchors (including `pyproject.toml` itself) to a wrong value and confirming the test failed in all seven cases before restoring them. That mutation check is a manual development step, not a test committed to the repository.

### Input limits

| Field            | Limit                                           | Paths            |
| ---------------- | ----------------------------------------------- | ---------------- |
| `goal`           | 1–2,000 characters, whitespace-only rejected    | `/plan`          |
| `screen_context` | ≤ 8,000 characters (optional, defaults to `""`) | `/plan`          |
| `content`        | 1–8,000 characters                              | `/memory`        |
| `query`          | 1–8,000 characters                              | `/memory/search` |
| `session_id`     | 1–256 characters, whitespace-only rejected      | all three        |
| `limit`          | integer 1–100 (default 3)                       | `/memory/search` |
| `metadata`       | object, defaults to `{}`                        | `/memory`        |

Models are strict: any extra field returns `422` with `extra_forbidden`.

### Verification appendix

Neither Ollama nor network access is needed to verify the two envelopes and the limits:

```bash
bash ./cela.sh test                 # the whole suite is offline: no network, no Docker, no Ollama
bash ./cela.sh api-surface --check  # the public contract snapshot is unchanged
```

Against a live server (memory disabled):

```bash
bash ./cela.sh services-up-api

# Envelope B — 422 with detail
curl -s -X POST http://127.0.0.1:8000/plan -H 'Content-Type: application/json' -d '{}'
curl -s -X POST http://127.0.0.1:8000/plan -H 'Content-Type: application/json' -d '{"goal":"read","session_id":" "}'
curl -s -X POST http://127.0.0.1:8000/plan -H 'Content-Type: application/json' -d '{not json'
curl -s http://127.0.0.1:8000/nope     # 404 detail
curl -s http://127.0.0.1:8000/plan     # 405 detail

# Envelope A — 409 memory_disabled
curl -s -X POST http://127.0.0.1:8000/memory -H 'Content-Type: application/json' -d '{"session_id":"s","content":"text"}'

# /health calls no model
curl -s http://127.0.0.1:8000/health
```

The remaining rows of Table A require the fault condition itself (stopping Ollama, corrupting the memory store, or injecting an exception) and are covered automatically in `tests/test_server.py`: `UnexpectedErrorMiddlewareTests`, `test_unexpected_errors_return_a_stable_json_500_without_details`, and `test_a_sanitized_500_still_answers_a_client_that_surfaces_exceptions`.

### Tagging options

Create the tag on the **merge commit in `main`**, not on a work commit inside the PR branch; tagging an unmerged branch points at a tree nobody receives.

**Option 1 — annotated tag on the merge commit (recommended here).** `main` is the only development line and there are no maintenance branches, so a tag is a marker, not a branch:

```bash
git checkout main && git pull --ff-only
git tag -a v1.0.1 -m "CELA.sh 1.0.1"
git push origin v1.0.1
```

**Option 2 — tag an explicit SHA** to pin the marker even if `main` moves before you push:

```bash
MERGE_SHA=$(gh pr view 17 --json mergeCommit --jq .mergeCommit.oid)
git tag -a v1.0.1 "$MERGE_SHA" -m "CELA.sh 1.0.1"
git push origin v1.0.1
```

**Option 3 — no tag.** The repository's stated policy is "one current version, no historical release line." Keeping `CHANGELOG.md` alone is literally consistent with it, and tagging is an editorial choice rather than a technical necessity. If you choose this, the six version numbers stay bumped and the guard stays active.

### Publishing

```bash
# Arabic notes as the release body
gh release create v1.0.1 --title "CELA.sh 1.0.1" --notes-file release-notes-ar.md

# English as a comment on the same release — no second release, no second table
gh release comment v1.0.1 --body-file release-notes-en.md
```

`gh release comment` does not pin the comment automatically; pinning is done from the GitHub UI on the release. The alternative, if you want English inside the release body itself:

```bash
cat release-notes-ar.md <(printf '\n\n---\n\n') release-notes-en.md > /tmp/notes-1.0.1.md
gh release create v1.0.1 --title "CELA.sh 1.0.1" --notes-file /tmp/notes-1.0.1.md
```

In both cases the reference table stays single: both files re-display `docs/api-errors.md`.

### Security note

The API is **unauthenticated**, and `session_id` is a selector, not an authorization. Compose publishes the port on host loopback only. Do not expose the service to an untrusted network before adding authentication and authorization. See [`SECURITY.md`](https://github.com/celiaelazamey-arch/computer_use/blob/main/SECURITY.md) and [`docs/threat-model-cela.md`](https://github.com/celiaelazamey-arch/computer_use/blob/main/docs/threat-model-cela.md) (item T11).
